# Audit + bug-fix run - 2026-10-31 (evening)

Ordered by Duckets after the new seat "kept doom looping in chat and
terminal". Everything below was reproduced before it was fixed, and
each fix names its verification. Plain words first, details after.

## What was actually broken

1. **The new seat could not stop talking.** The pristine
   Qwen/Qwen3.5-4B ships no `generation_config.json`, and the MLX
   conversion wrote `eos_token_id: None` into its config. LM Studio
   therefore never ended a generation: every reply ran to the token
   cap, in chat and in the guest terminal alike.
   Fix: the folder now carries the family `generation_config.json`
   (eos [248046, 248044], pad 248044, the vendor sampling defaults).
   Verified: probes end with finish_reason stop - Paris in 265
   tokens, a framed tool call in 41, the delegation probe in 71.

2. **The base brain thinks itself to death.** With thinking open,
   Qwen3.5-4B base spends its whole budget in `reasoning_content`
   and returns empty content on any harness-shaped prompt - 6 of 6
   full-SYS probes empty at 4096 tokens, still empty at 8192, at
   two temperatures, in both roles. Worked examples alone succeeded
   exactly once in three draws. `enable_thinking: false` passed as
   an API kwarg changed nothing through the MLX engine, and the
   engine rejects assistant prefill (HTTP 400).
   Fix (serving-side, on our converted artifact only): the library
   folder's `chat_template.jinja` now always emits the pre-closed
   think block (`<think>\n\n</think>`) as the generation prompt -
   the model's own template branch for thinking-off, made
   unconditional. Original kept as `chat_template.jinja.orig`.
   Verified: the same full-SYS prompt that emptied 6 times now
   answers in 35 tokens with the correct first tool call; plain
   chat unaffected ("The capital of France is Paris.", 7 tokens).
   This is also the measured answer to "is it worth a small tune":
   yes - a tune is what makes this unnecessary; until then the
   template carries the seat.

3. **Console answers could be stolen by stray typing.** The guest
   agent reads the model's replies from the same console stream a
   human types into. One stray line (an operator's own check
   command) was consumed as a model reply and printed as the
   session's final answer. Root cause: host answers and human
   input were indistinguishable.
   Fix (the QWENANS protocol): every host-fed answer is prefixed
   `QWENANS:` (`linux.py` line feed; `fastmachine.py` ANS frames -
   which also gained linux.py's flatten-to-one-line parity). The
   guest readers (`agent.sh` qwen_ask, `ask.sh` read_ans) accept
   only marked lines, strip the marker, and log anything skipped.
   The MMIO face and the bare-metal mailbox never had the problem
   and are untouched.
   Verified live: `QWENANS:The capital of France is **Paris**.`
   -> clean `QWEN_ANSWER:`, supervisor back at its prompt.

4. **The model echoes the task back.** On the plain base, a session
   reply can be the task itself, re-labelled `TASK:` (the
   dashboard's delegation syntax leaking into the guest protocol's
   shape). The harness catch-all delivered it as the final answer.
   Fix: agent.sh task-echo guard - a reply starting with `TASK: `
   is blocked with a nudge ("that is not doing it") and redrawn,
   bounded by the existing 9-round cap.
   Verification: pending the first live session on the new build.

5. **The dashboard hid a failure.** A finished circuit run that
   FAILED still displayed as "not running". `_status` and
   `/api/activity` now read the grown log for the verdict marker
   and the Overview says FAIL - finished, in plain words, with the
   reason (round limit on the old brain).

6. **Chat showed its own plumbing.** The dashboard only caught
   `TASK:` at line start; the model embedded one in prose
   ("just ask! TASK: write file ...") and then invented the
   result. The finder now takes the job from `TASK:` anywhere in
   the line, and the final-round cleanup cuts `TASK:` segments
   out of kept lines too.

7. **Two test drivers fed installs blind.** bridgetest.py and
   snapshot.py still used blind 256-byte chunk feeding - the class
   that tears heredocs on this guest. Both now use the verified
   pattern (line-paced `units_of()` feeding, in-guest md5 check,
   retry up to 3). snapshot.py's prime() also caught up with the
   framework: it installs ask + agent + agentshell, seeds SOUL,
   and lands at the supervisor prompt. The on-disk shell.snap is
   still the OLD priming - re-prime before relying on it.

8. **A null-content crash waited in the backend.** qwenbackend
   `ask()` stripped `content` unguarded; a reasoning-only reply
   (content null) would have raised instead of returning the
   `[qwen: empty answer]` sentinel. Guarded.

9. **The soul was a placeholder.** The guest's /root/SOUL.md was a
   one-liner written for the seed, and the dashboard prompt's
   header made the model introduce itself as "SOUL". Both now
   carry the real thing: the Hermes Agent SOUL.md (Nous Research,
   hermes-agent `hermes_cli/default_soul.py`) re-homed as
   `env/linux/SOUL.md` - its behavioral text kept (be direct,
   match reply length to the ask, no filler, plain claims, depth
   is earned), the identity pointed at this machine. Its first
   ~300 chars carry identity + directness because agent.sh folds
   only that much into wake-up prompts. liveterm.py and
   snapshot.py seed it from that single file; the dashboard's
   default prompt opens "WHO YOU ARE." and works the same
   directness rules into the chat. Verified: the chat's
   who-are-you answer is one clean sentence and no longer names
   itself SOUL; the live guest's /root/SOUL.md is the new file
   (838 bytes, read back).

10. **Chat sat "working" while the brain kept running** (reported
    live by Duckets during this audit). The page ends its working
    state only when the stream closes, and the stream stayed open
    because the handler kept working: the delegation finder
    scanned for `TASK:` ANYWHERE in the reply, so when the model
    merely explained the mechanism ("just ask! TASK: ...") the
    dashboard silently retracted the answer, typed the job into
    the guest (even mid-install, where it queued behind the
    installer), waited out a 300 s deadline, then generated more
    rounds - up to ~20 minutes of intermittent generation for one
    message. Three-part fix: delegation fires only when the reply
    LEADS with the TASK: line; `_guest_task` first checks the
    terminal is actually sitting at the agentshell prompt and
    otherwise reports "computer is busy" immediately instead of
    typing into a busy console; the wait deadline is 120 s, the
    page honours the server's done event, and the server closes
    the connection explicitly. Verified: the who-are-you question
    (whose answer itself mentions `TASK: <job>` in backticks) now
    completes with the stream closed after ~1 s, no retraction,
    no delegation.

  copy of qwen3.5-4b-mlx only. The Qwenputer checkpoint and the
  circuit executors do not use it and are unaffected.
